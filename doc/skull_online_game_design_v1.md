# Skull 线上多人互动游戏设计文档

**版本：** V1.0（设计初稿）  
**日期：** 2026-10-16  
**平台：** 桌面浏览器优先，兼容移动浏览器  
**规则基线：** Space Cowboys / Asmodee 2023 版 Skull

> 设计定位：把线下《Skull》的暗置、诈唬、竞价和逐张揭示转化为可信、低延迟、可重连的线上多人对局。规则由服务端权威执行；客户端负责清晰呈现动作、隐藏信息和情绪节奏。

> 知识产权提醒：原型请使用原创美术。若公开发布或商业化，先评估名称、规则文本及视觉素材的授权与知识产权风险，不直接复制官方 Logo、卡面或说明书插图。

## 1. 项目概述

### 1.1 目标与范围
- 3–6 人私人房间，房间码邀请；房间创建、加入、准备、开始、完整对局、断线重连、结算与再开一局。
- 竞价状态、当前行动人、弃权状态、翻牌历史均实时同步；对隐藏牌进行服务端保护。
- 暂不实现快速匹配、观战、好友系统、语音/视频、商城、真钱、赛季/锦标赛。
- 后续可扩展排行榜、战局回放、主题皮肤、多语言、公开匹配。

### 1.2 核心原则
1. 服务端权威：客户端不决定胜负、不自行扣牌、不自行判断翻牌是否合法。
2. 隐藏信息最小化：未揭示圆片类型永不发送给无权知道的客户端。
3. 事件驱动与可恢复：动作带序列号；房间状态可快照、可重放、可重连。
4. 规则与表现分离：先结算状态，再播放动画；动画失败不能影响规则。

## 2. 规则基线与线上判定

采用 2023 版 Skull 规则，而非早期 Skull & Roses 旧版规则。每名玩家初始 4 枚圆片（3 花、1 骷髅），每人有一个双面玩家垫，另有全局“最后机会”圆片。[1][2]

### 2.1 胜利条件
- 每次成功挑战：若玩家垫为空白面，翻至花面；若已是花面，再次成功挑战即获胜。
- 若其他玩家全部淘汰，最后存活者获胜。

### 2.2 每轮流程
1. **初始暗置：**每名存活玩家秘密暗置 1 枚圆片。先手需等待其他玩家放好后，最后放自己的第一枚。
2. **追加或开价：**从先手开始顺时针。可以追加一枚，或开价宣布能安全翻开的圆片数；先手可直接开价。
3. **竞价：**开价后不能追加。轮到玩家时只能提高当前报价或弃权。报价必须严格高于当前报价且不超过场上暗置圆片总数；可一次加多个。
4. **决出挑战者：**弃权的玩家不能重新进入本轮竞价；直到只剩一名未弃权玩家，其成为挑战者。
5. **逐张揭示：**挑战者每次翻一枚，必须先翻自己的圆片，之后才能翻其他玩家。只能翻某堆最上方尚未揭示的圆片。
6. **结算：**达到报价且没翻到骷髅则成功；一旦翻到任何骷髅，立即失败并停止翻牌。

### 2.3 失败扣牌
- **翻到其他玩家的骷髅：**挑战者把本轮已放置与手中未放置的圆片合并、背面朝上洗混；骷髅所属玩家盲选一枚放回盒中，不查看正面。
- **翻到自己的骷髅：**挑战者收回自己所有已放置和未放置圆片，并秘密选择一枚放回盒中。
- 扣牌后剩 0 枚：玩家淘汰，移除玩家垫。
- 扣牌后恰剩 1 枚：若本局尚未获得过最后机会圆片，则获得它，在下一轮使用一次。

### 2.4 最后机会圆片
- 只在失败扣牌后仍恰剩 1 枚自有圆片、且本局未曾获得时发放；它是一枚公开已知的花。
- 只在下一轮有效；下一轮结束时归还供应区。
- 若使用最后机会圆片的一轮中，玩家作为挑战者失败，则同时失去最后机会圆片和自有最后一枚圆片并淘汰。

### 2.5 下一轮先手与终局
- 挑战者存活：挑战者成为下一轮先手。
- 挑战者被其他玩家的骷髅淘汰：骷髅所属玩家成为下一轮先手。
- 挑战者因翻到自己的骷髅而淘汰：其选择下一轮先手。
- 达到第二次成功挑战或只剩一名存活者，立即结束整局。

> 弃权只退出当前竞价，不等于淘汰；扣掉一枚圆片也不必然淘汰。超时、断线和房间运营策略需要与桌游规则分开配置。

## 3. 功能需求与交互

### 3.1 房间流程
- 游客昵称进入；创建者成为房主并获得 6 位房间码。
- 房间支持 3–6 人；展示座位、昵称、在线状态和准备状态。
- 所有人准备且人数不少于 3 才可开始；MVP 不允许开局后加入。
- 结算展示胜者、胜利方式、对局时长和基础统计；支持再开一局。

### 3.2 主桌面布局
- **中央区域：**轮次阶段、最高报价、场上暗置圆片总数、挑战者与揭示进度。
- **玩家区域：**昵称、玩家垫正反面、暗置圆片数量、是否弃权、剩余圆片数量、在线状态。
- **操作区：**依据当前阶段提供放置、开价、加价、弃权、选择牌堆翻牌等按钮。
- **揭示阶段：**高亮合法目标；每次只揭示一枚；呈现已安全翻开数与剩余目标。
- **无障碍：**状态不只靠颜色区分，同时配文案/图标；动画可关闭，支持键盘焦点。

### 3.3 关键细节
- 暗置后所有其他客户端只看到背面和数量；不得通过事件、缓存、错误信息或日志泄漏类型。
- 开价必须是正整数，不超过暗置总数；开价后禁用追加。
- 弃权者不能再竞价，但其圆片仍可被挑战者翻开。
- 若挑战者仍有未揭示的自有圆片且尚未达到报价，不允许先翻其他玩家。
- 可先提供预设表情/短句；自由聊天放在后续版本并配套审核能力。

## 4. 规则引擎与状态机

### 4.1 状态
`LOBBY → ROUND_SETUP → INITIAL_PLACEMENT → ACTION → BIDDING → REVEAL → (PENALTY) → ROUND_CLEANUP → 下一轮或 FINISHED`

- **LOBBY：**加入、离开、准备、房主开始。
- **ROUND_SETUP：**清理上一轮，设置先手与最后机会圆片。
- **INITIAL_PLACEMENT：**每名存活玩家放置第一枚，先手最后放。
- **ACTION：**放置一枚或开价；手中无普通圆片可放时必须开价。
- **BIDDING：**加价或弃权，直到只剩一名未弃权玩家。
- **REVEAL：**挑战者逐张揭示，成功或翻到骷髅后结算。
- **PENALTY：**扣牌、淘汰、最后机会处理及确定下一轮先手。
- **ROUND_CLEANUP：**回收本轮圆片、归还到期的最后机会圆片、检查终局。
- **FINISHED：**锁定结果，允许再开一局。

### 4.2 核心数据对象
- `Room`: `roomId, roomCode, hostPlayerId, phase, rulesetVersion, settings, stateVersion`。
- `Player`: `playerId, seatIndex, displayName, connected, ready, alive, matSide, lastChanceGranted, lastChanceActive`。
- `Disc`: `discId, ownerPlayerId, type, location, roundId, stackIndex, revealed`。
- `Round`: `firstPlayerId, currentPlayerId, currentBid, highestBidderId, passedPlayerIds, challengerId, revealCount, revealHistory`。
- `Event`: `eventId, roomId, stateVersion, actorId, actionType, publicPayload, privatePayloadRef, createdAt`。

隐藏牌类型不得写入所有玩家都可读取的公共事件。

### 4.3 规则引擎接口
```ts
applyAction(gameState, actorId, action) -> { nextState, emittedEvents }
```
- 纯状态转移，不原地修改输入；非法动作返回明确错误码。
- 合法动作使 `stateVersion` 单调递增；`actionId` 幂等，防止重试导致重复结算。
- 抽洗、惩罚、淘汰、最后机会与终局判定均由服务端处理。

## 5. 技术架构

### 5.1 推荐 MVP 技术栈
| 层次 | 方案 | 职责 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 响应式桌面、操作、动画、重连 |
| 实时通信 | WebSocket / Socket.IO | 动作提交、状态推送、断线检测 |
| 业务服务 | Node.js + TypeScript（NestJS 或模块化服务） | 房间管理、规则引擎、校验和结算 |
| 持久化 | PostgreSQL | 快照、事件日志、对局结果 |
| 可选扩展 | Redis | 多实例扩展时的在线状态、路由和发布订阅 |

### 5.2 原则
- 同房间动作串行化，避免同时加价引发竞态。
- 前端可做预校验，但服务端必须重复校验。
- 公共状态与个人私有状态分开构造，向不同玩家发送个性化快照。
- 更新状态/持久化成功后再广播；动画不参与事务。
- MVP 可单实例部署；扩展到多实例后再引入 Redis 和房间分片。

## 6. 通信协议、安全与恢复

### 6.1 客户端命令
`room.create`、`room.join`、`room.ready`、`room.start`、`game.place_disc`、`game.open_bid`、`game.raise_bid`、`game.pass`、`game.reveal`、`game.choose_penalty_disc`。

服务端必须校验阶段、轮到谁、玩家是否存活、圆片归属和位置、竞价范围、揭示顺序，以及惩罚选择权限。不能信任客户端上传的玩家身份和牌面类型。

### 6.2 公共事件
`ROUND_STARTED`、`DISC_PLACED`（仅数量公开）、`BID_OPENED`、`BID_RAISED`、`PLAYER_PASSED`、`DISC_REVEALED`、`CHALLENGE_SUCCEEDED`、`CHALLENGE_FAILED`、`DISC_REMOVED`、`PLAYER_ELIMINATED`、`LAST_CHANCE_GRANTED`、`ROUND_ENDED`、`GAME_ENDED`。

所有消息携带 `roomId/stateVersion/eventId`。客户端发现版本跳跃时请求个性化完整快照。未揭示圆片不可包含 `type`、牌面资源名或可反推类型的调试字段。

### 6.3 断线与超时
- 断线玩家保留座位，默认 60 秒重连宽限；房主离开则转交给最早加入且在线的玩家。
- 房间可设置行动计时关闭/30/60/90 秒。竞价超时视为弃权；放置阶段可由服务端从合法圆片中随机选择；揭示阶段可自动选择顺时针第一个合法牌堆。该机制属于线上防拖延规则，开始前必须公示。
- 服务端重启从快照与之后事件恢复；不能静默重置牌局。

## 7. 测试与验收

### 7.1 必测用例
1. 3 人/6 人边界与开始条件正确。
2. 先手初始放置必须最后完成。
3. 报价正整数、严格递增、不超过暗置总数。
4. 开价后尝试放牌必须被拒绝。
5. 弃权后再次竞价必须被拒绝，弃权者牌堆仍可揭示。
6. 挑战者必须先翻自有圆片；每次只翻一枚、只能翻最上方未揭示圆片。
7. 成功挑战正确翻垫子；已是花面时再次成功获胜。
8. 翻到他人骷髅时由骷髅主人盲选扣牌；翻到自己骷髅时挑战者秘密自选扣牌。
9. 剩 0 枚淘汰；剩 1 枚且符合条件时获得最后机会圆片。
10. 最后机会只作用下一轮、轮末归还、规定失败场景同时失去两枚。
11. 下轮先手、第二次成功挑战胜利、最后存活胜利均正确。
12. 同一 `actionId` 重复提交不产生副作用。
13. 翻牌前，非本人客户端无法从任何网络/日志途径得到牌面类型。
14. 断线恢复后状态一致且不重复结算。

### 7.2 非功能标准
- 正常网络下服务端动作确认 P95 建议低于 300ms（不含动画和极端网络延迟）。
- 支持 6 人同局及多房间并发；覆盖并发加价、断线重连和服务重启。
- 规则单元测试、随机合法动作测试、WebSocket 集成测试和浏览器端到端测试均需覆盖。
- 属性测试检查圆片守恒：初始总数等于手中 + 暗置/揭示 + 已移除 + 供应区。

## 8. 迭代计划与风险

| 阶段 | 交付 | 完成标准 |
|---|---|---|
| P0 规则核心 | 数据模型、RulesEngine、单元测试 | 脚本能模拟整局，关键规则测试通过 |
| P1 可玩 MVP | 房间码、实时通信、桌面 UI、完整对局 | 多浏览器从创建房间玩到终局且状态一致 |
| P2 稳健性 | 重连、快照、版本、幂等、计时与限流 | 重复包、断线和服务重启测试通过 |
| P3 体验优化 | 动画、音效、快捷表情、移动适配 | 桌面和移动端可顺畅操作 |
| P4 扩展 | 快速匹配、回放、排行榜、多实例 | 按用户反馈确定优先级 |

主要风险：规则理解不一致、隐藏信息泄漏、竞价竞态、断线拖延和美术/商标授权。通过规则版本化、规则测试、公共/私有 payload 隔离、动作串行化、重连/计时策略及原创美术应对。

## 9. 待确认决策
- 第一版只做私人房间，还是包含公开快速匹配？本文默认私人房间。
- 行动计时默认关闭还是 60 秒？本文建议房主可配置，公开匹配强制计时。
- 是否提供自由聊天？本文建议 MVP 先做快捷表情/短句。
- 是否将失败后“其他玩家展示圆片”的可选社交动作纳入第一版？它不影响结算，可延后到 P3。
